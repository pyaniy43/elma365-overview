# Отчёт: поиск нетипичного поведения заявок на закупку (Кейс 1)

## 1. Инструменты и воспроизводимые шаги

Анализ я выполнил на Python 3 + pandas (скрипты лежат в этой же папке: `detect_anomalies.py`, `analyze_routes.py`, `durations.py`). Порядок действий:

1. Загрузил `students.csv` как UTF-8 с BOM, все поля — строки; `Timestamp` разобран как datetime с часовым поясом и переведён в UTC для расчёта длительностей, а для контроля календаря — в Europe/Moscow.
2. Внутри каждого `ProcessInstanceId` отсортировал события по числовому `EventIndex` и восстановил маршрут как последовательность этапов с результатами (`accept / return / reject`) и фактической ролью исполнителя.
3. Посчитал длительность каждого задания (`task_completed.Timestamp − task_created.Timestamp` по тому же `TaskId`).
4. Проверил соответствие ролей этапам (кросс-таблица «этап × роль»), порядок этапов, обязательность этапов для каждого `RequestType`, число возвратов, наличие внеплановых проверок и выбросы длительностей.

Скрипт `detect_anomalies.py` воспроизводит итоговый `anomalies.csv` за один запуск.

## 2. Что считается обычным поведением

В журнале **1000 процессов, 12 162 события**; 990 завершено (939 `fulfilled`, 51 `rejected`), 10 открыто на дату среза. Типы: standard 635, contract 197, urgent 168.

Типичный успешный маршрут (подтверждён 622 + 150 процессами):

- **standard / urgent**: Регистрация → Проверка заявки → Согласование руководителем (accept) → Согласование бюджета → Исполнение → Завершение (fulfilled).
- **contract**: то же, но между бюджетом и исполнением добавляется «Проверка договора» юристом.
- **Возврат** (119 процессов с 1 возвратом): руководитель делает `return` → «Доработка заявки» заявителем → повторная проверка → повторное согласование руководителем → далее по схеме.
- **Отказ** (44 процесса): руководитель делает `reject` → процесс завершается `rejected` (без бюджета/исполнения).

Соответствие ролей строгое: Проверка — specialist, руководитель — manager, бюджет — finance, договор — legal, исполнение — procurement, доработка — requester, внеплановая проверка — auditor. Единственное нарушение этого правила — 8 задач руководителя, закрытых заявителем (см. ниже).

Типичные длительности (медиана): Проверка заявки ≈ 0.36 ч, руководитель ≈ 1.85 ч, бюджет ≈ 2.43 ч, проверка договора ≈ 17 ч, исполнение ≈ 18 ч. Все 12 162 события лежат внутри рабочего календаря (пн–пт 09:00–18:00 MSK) — событий вне рабочего времени не обнаружено. Суммы положительные (2 111–255 786 усл. руб.), нулевых и отрицательных нет.

## 3. Критерии аномальности

| Критерий | Тип | Причина выбора |
|---|---|---|
| Роль на этапе «Согласование руководителем» ≠ manager | Самосогласование | Нарушение разделения обязанностей (заявитель не может сам утверждать свою заявку) |
| Исполнена (`fulfilled`), но нет этапа руководителя | Пропуск этапа руководителя | Руководитель — обязательный этап по схеме |
| «Исполнение» раньше «Согласования бюджета» (и «Проверки договора») | Исполнение до согласования | Закупка не должна начинаться до одобрения бюджета/юриста |
| Два подряд «Проверки заявки» без возврата между ними | Дубль проверки | Повторный этап не объяснён бизнес-логикой (возврат отсутствует) |
| ≥3 возвратов на доработку | Многократный возврат | Типично 0–1 возврат (873 процесса без возвратов, 119 с одним) |
| Наличие «Внеплановая проверка» аудитором | Внеплановая проверка | Дополнительная проверка требует отдельного обоснования; по редкости не отклоняется |
| Длительность «Проверки заявки» ≥ 150 ч | Аномально долгая проверка | Медиана ≈0.36 ч, 99-й перцентиль ≈70 ч — явный выброс |

Порог «≥3 возвратов» и «≥150 ч» взят по фактическому разрыву в распределении: возвраты бывают 0, 1 и сразу 5–8 (значений 2–4 нет); длительности проверок имеют ровно 8 выбросов 198–261 ч при следующем максимуме ≈63 ч.

## 4. Результаты

Найдено **64 строки отклонений для 56 уникальных процессов** (у части процессов — по два отклонения, они вынесены отдельными строками):

| Тип | Строк | Суть |
|---|---|---|
| Самосогласование | 8 | 7 раз заявитель сам утвердил заявку, 1 раз — сам отклонил |
| Пропуск этапа руководителя | 16 | исполнено без согласования руководителем |
| Исполнение до согласования | 8 | 5 — исполнение до бюджета; 3 — до бюджета и юрпроверки |
| Дубль проверки | 8 | две проверки подряд без возврата |
| Многократный возврат | 8 | 5–8 циклов доработки (5, 6×3, 7, 8×3) |
| Внеплановая проверка | 8 | по 2 задачи аудитора в маршруте |
| Аномально долгая проверка | 8 | проверка длилась 198–261 ч |

**Показательные примеры:**

- `35097b8a-…` (standard, 31 370.82): этап «Согласование руководителем» закрыт ролью `requester` — заявитель утвердил собственную заявку.
- `4d1f084c-…` (standard, 99 110.45): исполнена без этапа руководителя, маршрут «Проверка → Бюджет → Исполнение».
- `b47a3061-…` (contract): «Исполнение» выполнено раньше «Согласования бюджета» и «Проверки договора» — закупка начата до одобрений.
- `17b4a994-…` (urgent): «Проверка заявки» длилась 261 ч (≈11 суток) при медиане 0.36 ч; этот же процесс пропустил этап руководителя.

**Интересная связь:** все 8 процессов с аномально долгой проверкой одновременно входят в 16 процессов, пропустивших этап руководителя. Это похоже на единый сценарий «заявка зависла на проверке и затем была проведена без согласования руководителя».

## 5. Ограничения, ложные срабатывания, ручная проверка

- **Внеплановая проверка (8)** — не нарушение само по себе: аудитор может участвовать во внеплановой проверке, и её оправданность нельзя установить по редкости. Помечено как «требует ручной проверки», а не как жёсткое нарушение.
- **Многократный возврат (8)** — формально процесс допускает повторные возвраты; 5–8 циклов технически возможны, но статистически необычны. Стоит проверить, не ошибка ли это данных/зависание, а не однозначное нарушение.
- **Аномально долгая проверка (8)** — длительность включает ожидание, поэтому это может быть очередь/отпуск, а не ошибка; но 198–261 ч против медианы 0.36 ч требуют ручной проверки причины задержки.
- **Дубль проверки (8)** — может быть как лишним этапом, так и особенностью выгрузки; проверить, действительно ли задача создавалась дважды.
- **Открытые процессы (10)** — сами по себе не аномалия (8 остановились на проверке, 2 на бюджете на дату среза); в `anomalies.csv` не включены.
- Длительности исполнения (медиана 18 ч, много задач 66–72 ч) не считались аномалией: исполнение реально занимает дни, а значения ~70 ч — это задача, перешагнувшая выходные.
- В данных нет событий вне рабочего времени, отрицательных/нулевых сумм и «висячих» завершений без создания задачи — эти проверки не дали кандидатов.

## 6. Использование ИИ

Анализ я выполнял самостоятельно; ИИ-ассистент (DeepSeek) использовался точечно — как помощник при написании pandas-скриптов, проверке синтаксиса и написании отчёта. Постановка гипотез, восстановление маршрутов, выбор критериев и порогов, а также вся интерпретация результатов — мои.

Проверка результатов (в том числе ответов ассистента):

- контрольные суммы сходятся ровно к 1000 процессам, распределение возвратов — к 1000, число задач «создано/закрыто» — к 4 591/4 581 (разница 10 = открытые процессы);
- каждую категорию я точечно перепроверил вручную по `students.csv`: открывал конкретные `ProcessInstanceId`/`TaskId` и сверял роль, результат и длительность;
- пороги (≥3 возвратов, ≥150 ч проверки) выведены из самих распределений — разрыв между 0–1 возвратом и 5–8, выбросы 198–261 ч против медианы 0.36 ч, — а не подогнаны под ожидаемый ответ.
